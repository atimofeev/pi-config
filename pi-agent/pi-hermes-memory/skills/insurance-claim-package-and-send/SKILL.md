## When to Use
Use when reimbursable receipts already archived in Paperless must be turned into a submission-ready insurance package: several receipts grouped into insured events, one folder per event with a signed claim form and the supporting reports, plus email drafts the user will send from their own mailbox. Fits any insurer or employer claim process where form filling itself is handled by the companion form-filling procedure. Applies to NixOS hosts where tooling is used ephemerally, and to Paperless instances whose receipts may be phone photos rather than PDFs.

## Procedure
1. Enumerate what is claimable. Query the archive for receipts and subtract those already submitted, then list each receipt's provider, date and amount. Cross-check the total against any note you wrote earlier; do not trust the note. Confirm nothing is left unclaimed by matching every receipt in the archive to some claim folder by provider and date, since scan-style titles hide the identity.
2. Extract the facts per receipt and per supporting document. From receipts take provider, printed address, invoice date, patient name as printed, itemised services with prices, and total paid. From medical reports and lab results take visit or sample date, provider, diagnosis or impression, findings, therapy and ordered procedures. Mark anything uncertain and quote the raw fragment rather than guessing.
3. Group receipts into insured events using date proximity and clinical narrative, then have the user confirm the grouping before generating anything. Ask explicitly about: ambiguous diagnoses and whether to transcribe or normalise them; receipts that mix items from two conditions; and whether one draft per event or one per person is wanted.
4. Create one folder per event under a single archive directory, named `YYYY-MM-DD-<patient>-<treatment>` where the date is the submission date so that new claims sort last. Write a README at the top level describing the convention, the standing recipients, and any open questions.
5. Download the originals through the REST API with the `original=true` parameter, writing straight to files so bytes never travel through the model context. Read each document's `mime_type` first and name the file with the matching extension.
6. Convert photo scans to single-page PDFs at about 200 dpi and verify legibility by rendering a page and reading it back. Keep the full-resolution originals in the archive only, and say so in the README so nobody thinks evidence was discarded.
7. Fill and sign the claim form for that event, following the separate form-filling procedure. Then persist the filled values to a `form-values.json` beside the form, so later steps can read the patient, policy, event date, diagnosis and amount without re-parsing the PDF.
8. Write the email package per claim: an `.eml` holding recipients, subject, body and all attachments, plus a `draft-info.txt` with the same content as plain text. In the body name the patient, their date of birth, the policy number, treatment date, institution, diagnosis and amount, and label each attachment by kind so the insurer can see at a glance what is enclosed.
9. Write a `send-instructions.md` in each claim folder containing the recipients block, a byte-faithful copy of the body in a fenced block, the numbered attachment list with sizes, the step-by-step manual send procedure, per-claim checks, and a short note explaining why an `.eml` cannot simply be imported. Add a top-level guide that compares the manual, client, IMAP and API routes honestly, marking the unverified ones as unverified.
10. Verify the package rather than assuming it. Confirm every attachment is a real PDF, every `.eml` parses, embedded attachment names and sizes equal the files on disk, the guide's paste-block matches the `.eml` body, policy numbers match the right person, no retired identifiers survive anywhere, and the claim amounts sum to the archive total for those receipts.
11. Hand the package over for manual sending. Do not send anything yourself, and do not mark receipts as submitted in the archive until the user confirms the messages went out.

## Pitfalls
- Paperless stores phone-photo uploads as `image/jpeg`, so `download/?original=true` returns a JPEG even for a document you assumed was a PDF. Writing those bytes to a `.pdf` name produces a file no PDF reader can open. Always read `mime_type` from the API and confirm with `file -b` before trusting a document's extension.
- Email encodes attachments as base64, which inflates them by roughly a third. A 24 MB attachment set becomes a ~32 MB message and blows past Gmail's 25 MB cap; above that cap Gmail silently replaces attachments with Google Drive links, which is unacceptable for medical documents. Size the packet against the *encoded* total, not the raw one.
- Uncompressed phone photos are 7-9 MB each. Convert them to single-page PDFs at about 200 dpi (long edge ~2200 px, JPEG quality ~82) and they land near 0.5 MB while staying clearly legible. Keep the untouched originals in the archive rather than shipping them in the email.
- Gmail cannot turn an `.eml` into a draft. Its *Import mail and contacts* feature moves messages into a label, the web UI has no upload-to-Drafts action, and dragging an `.eml` onto compose is not a documented capability. Do not promise an import path; paste from a prepared text block instead.
- Appending a raw message to `[Gmail]/Drafts` over IMAP is plausible and preserves MIME parts in principle, but the result being an editable web draft is unverified, as is thread behaviour. Have the user test with a throwaway message before relying on it.
- Receipts almost never carry a diagnosis. The diagnosis comes from the medical report for the same visit, and the report wording is often an abbreviation, a question mark, or plain garbled. Extract it, mark anything uncertain, and let the user decide whether to transcribe verbatim or normalise. Never invent a diagnosis.
- One form describes one insured event and carries one event date. When a consultation and its paid tests fall on different days, pick the consultation date deliberately and name every provider involved; leave the spread visible rather than pretending the receipts share a date.
- Group receipts into events by date proximity plus clinical narrative. A same-day pharmacy basket normally belongs with that day's consultation, but check the prescribed therapy matches, because the same day can hold two visits with two different prescriptions.
- An invoice is not proof of payment. A clinic invoice, even one stamped and signed, shows what was charged, not that money changed hands. If the insurer wants proof, a till receipt from the payment itself is what satisfies it.
- Never alter a third-party document, including retouching a scan to fix a clerical error. Put the clarification in the covering email instead, quoting both the printed and the correct spelling, and leave the invoice byte-identical to the provider's copy.
- Forms ask for names in the order their own labels dictate (often surname first), while an email reads naturally as given name then surname. Keep them different on purpose and do not "fix" either side to match the other.
- Include the patient's date of birth in the covering email: it lets the insurer match the insured person immediately. Verify it from the typed custom field AND from the ID scan read visually - automated OCR fails on these dates and on ID numbers, so OCR alone is not evidence.
- Check that every ordered test has a result document attached. An archive can hold only the receipt for a lab test and no result, which looks like an incomplete claim. Query the provider's documents by correspondent to prove whether a result exists before claiming the packet is complete.
- The same episode can touch a public provider and a private one. A public provider's form may carry the same diagnosis as a private invoice but a different prescription and no cost at all. Attach it as corroboration and say so, rather than implying it documents the payment.
- Tag-based asset lookups fail silently after a re-upload. A new upload often lands with no document type and no tags, so `type:signature AND tag:<person>` keeps returning the stale document while the replacement sits unnoticed. After any upload, set type and tags explicitly, then delete the old asset and re-run the lookup to confirm it returns exactly one document.
- Destructive Paperless operations require `confirm: true`, and a `socket connection was closed unexpectedly` error does not tell you whether the write landed. Re-read the object before retrying, or you risk deleting twice or editing the wrong thing.
- The document-replacement endpoint acknowledges before processing. A 200 response with a task id can be followed by an unchanged file and no new version for minutes. Poll the version count, and query the served file, before concluding the replacement failed - then retry if it truly has not landed.
- Derive every amount from the receipt itself, never by adding up a summary you wrote earlier. Re-sum the finished claim packages from their stored form values and compare against the archive, because a hand-written total in a README drifts from the forms.

## Verification
1. Every file intended as an attachment reports `PDF document` from `file -b` and opens with `pdfinfo`; a rendered page of each converted scan is readable, including the amount and fiscal codes on receipts.
2. Each `.eml` parses with the `email` module and its embedded attachment names and decoded byte sizes are identical to the files in the folder.
3. The paste-block in each `send-instructions.md` matches the `.eml` body apart from the markdown fence's trailing newline, which is cosmetic.
4. Every claim amount is re-derived from the form values and traced to the receipt it came from; the per-person and overall totals reconcile against the archive.
5. Every claim folder maps to at least one receipt and its policy number belongs to the named patient; a search for retired identifiers returns nothing.
6. No receipt present in the archive is absent from every claim folder - the unclaimed set is empty or explicitly listed.
7. The user has reviewed the drafts and confirmed the grouping, the diagnoses and the manual send procedure before anything is sent.
